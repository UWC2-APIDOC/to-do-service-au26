Use `GET /tasks?userId={id}` to retrieve one user's tasks.
The endpoint filters the tasks collection by the `userId` field.
This avoids retrieving every task when you only need a user's to-do list.

> **Environment:** This reference describes the repository's local JSON Server implementation.
> JSON Server supplies query filtering; it isn't a separate custom API route.
> The examples use `http://localhost:3000` with `api/to-do-db-source.json`
> and JSON Server 0.17.4.

## HTTP request

| Property | Value |
| --- | --- |
| Method | `GET` |
| Endpoint | `/tasks` |
| Query parameter | `userId` |
| Example URL | `http://localhost:3000/tasks?userId=5` |
| Request body | None |
| Authentication | None for the local JSON Server demo |
| Success status | `200 OK` |
| Response content type | `application/json` |

## Query parameter

| Name | Type | Required for this filter? | Description |
| --- | --- | --- | --- |
| `userId` | Number | Yes | Match tasks with this stored value; use an ID from `/users`. |

If you omit `userId`, `GET /tasks` returns the full tasks collection instead of filtering by user.

**Important:** The filter compares against the `userId` stored on each task. It does not verify
that the user exists in `/users`.

## Request example

```http
GET /tasks?userId=5 HTTP/1.1
Host: localhost:3000
Accept: application/json
```

### `cURL`

```bash
curl -i -X GET "http://localhost:3000/tasks?userId=5" \
  -H "Accept: application/json"
```

### Postman

1. Create a new **GET** request.
2. Enter `http://localhost:3000/tasks` in the URL field.
3. Open **`Params`**, enter `userId` as the key and `5` as the value (or use your actual user ID).
4. Click **Send**.

## Successful response

**Status:** `200 OK`

**Example response body:**

```json
[
  {
    "id": 12,
    "userId": 5,
    "title": "Prepare weekly report",
    "description": "Collect project updates and submit the summary",
    "dueDate": "2026-12-01T17:00",
    "warning": 30
  },
  {
    "id": 13,
    "userId": 5,
    "title": "Review project notes",
    "description": "Review the notes before the team meeting",
    "dueDate": "2026-12-03T09:00",
    "warning": 15
  }
]
```

The records illustrate the response structure. Task IDs, field values, and task counts depend on
your local database.

## Response fields

Each element in the JSON array is a task object. The application uses these task properties:

| Field | Type | Description |
| --- | --- | --- |
| `id` | Number | Unique task identifier generated by the local server. |
| `userId` | Number | ID of the user associated with the task. |
| `title` | String | Brief title of the task. |
| `description` | String | Additional details about the task. |
| `dueDate` | String | Task deadline as stored in the database (for example, `2026-12-01T17:00`). |
| `warning` | Number | Reminder lead time in minutes. |

JSON Server returns stored records; fields can vary with the contents of the data file.

## No matching tasks

If no tasks contain `userId: 5`, the server still returns **`200 OK`** with an empty array:

```json
[]
```

An empty array means _no matching tasks_; it does not prove that the user exists or does not exist.
To check the user, send `GET /users/5` separately.

## Errors and troubleshooting

| Result | Possible cause | Resolution |
| --- | --- | --- |
| `200 OK` and `[]` | No task matches `userId` | Use `GET /tasks` to find an ID, then retry. |
| `404 Not Found` | Wrong resource path, such as `/task` | Use the plural path `/tasks`. |
| Connection refused | JSON Server isn't running on port 3000 | Start it in `api`. |
| All tasks returned | `userId` omitted or misspelled | Use the exact key `userId`. |

## Verify the operation locally

From the root of a local clone, start the sample API:

```bash
cd api
json-server -w to-do-db-source.json
```

In a second terminal, list users and tasks to find a user ID with assigned tasks:

```bash
curl "http://localhost:3000/users"
curl "http://localhost:3000/tasks"
```

Then query tasks for that ID:

```bash
curl "http://localhost:3000/tasks?userId=5"
```

Replace `5` with an ID that appears in the `userId` field of at least one task to verify
 a nonempty response.

> **Documentation note:** This page describes read-only filtering. To create a task, use
> `POST /tasks`. To retrieve one task by its task ID, use `GET /tasks/{id}`. The
> two IDs are different: `userId` identifies the assigned user, whereas `id`
> identifies the task itself.
